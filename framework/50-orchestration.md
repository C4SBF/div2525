# 25.25.50 - Orchestration
This section relates to orchestrating, or directing and moving, data and information among applications, systems, storage, and, eventually, users. Div2525 as a whole describes how the building should work as a smarter building - which is to say, with functionality that depends on the interoperation of multiple building systems working together. This section 25.25.50 - Orchestration, is at the crux of making the building operate smarter, and not just as an assembly of separate, siloed systems, even if one or more of the systems is "smart" on its own. As noted in Section 25.25.40, the interoperability of applications is required to fulfill the intended occupant/tenant experience, operational requirements, and ownership goals. In a smarter building, data and information must be exchanged among various systems to enable this interoperability. This section 25.25.50 - Orchestration, discusses:
- The primary ways that data and information can be exchanged between systems in a building.
- Data and Information Portability
- What are well-behaved APIs?
- General requirements for data exchange
- Sample use case requirements

## 50.1 The Primary Ways Data and Information Can Be Exchanged

### 50.1.1      Communication Protocols

Communication protocols are rules and procedures that govern data exchange between two or more devices or systems. The protocol specifies how data is transmitted, received, and processed, and typically includes rules for error detection and correction, data compression, encryption, and other aspects of data transmission. Communication protocols can be specific to a particular domain, such as HVAC or lighting, or more general-purpose, such as the TCP/IP protocol used by the Internet and many systems in buildings. The 'data and information exchange' defined under 25.25.50 should strive to use a specific protocol when the systems involved natively understand the protocols. Protocol converters or gateways can be used when systems do not understand a common protocol. Always ensure that the correct protocol is selected for the intended purpose: some protocols have multiple versions and variants for different applications.

Protocols may be specified and maintained by formal standards bodies, or they may be a de facto standard in specific domains. Using formal standards is always the best option when available. The best approach to selecting a protocol is to identify the systems/devices being connected, the exact purpose of such connections, and the specifics of the data that needs to flow to achieve the stated purpose.

### 50.1.2      Gateways and Converters

A gateway is a network node that acts as an entrance or an exit point for data traffic between different networks. It can be hardware, software, or a combination of both, and it performs various functions such as protocol translation, data routing, and security filtering. Gateways are often used to connect networks with different protocols or architectures, such as between systems from different vendors using different protocols or systems having different network topologies, control rules, and ownerships. Gateways can provide a useful way to connect systems in buildings, but one must ensure suitability for the purpose. Gateways must work for the life of the building and systems involved; this can especially challenging when a protocol's versions and requirements are likely to change over time.

### 50.1.3      Middleware Exchange

Middleware refers to software components or services that are located between other applications, systems, or components, and enable them to communicate and exchange data through the middleware. Middleware provides a common platform for different applications to interact with each other by handling common tasks such as data transformation, message routing, authentication, and security. Middleware allows different systems to communicate with each other without having to know the details of each other's implementation or technology. Middleware can be considered a collection of gateways, often with a common normalizing protocol at its center. This normalizing protocol is often proprietary. For example, system 1 would use a specific protocol to communicate with the Gateway, which would be converted to the Middleware's common, often proprietary data structure and made available to other systems. This way, system 2, connected to the Gateway, could access System 1's information suitably converted to the protocol it understands. Middleware can suffer from challenges that are similar to what protocols and gateways experience. For example, if a system's understanding of a protocol changes after an upgrade, the gateway may be unable to convey information correctly, potentially in some subtle, and not immediately noticeable, way. Another challenge is that middleware does not scale well to larger and more complex scenarios which may create a single point of failure in the building.

### 50.1.4      Ontologies

In computer science, an ontology is a formal description of knowledge/information? representing the entities, concepts, and relationships within a domain. The ontology consists of a set of concepts or categories related to each other in a hierarchical or networked structure, and it defines the relationships and properties between these concepts.

The ontology of a building system is a structured way of defining and organizing the knowledge about the components that make up the building system. An increasingly popular form of ontology in buildings is tagging data about buildings. For example, a sensor may produce a value of 74, but the sensor data is of little use unless you also understand that it is a temperature that's measured in degrees Fahrenheit. Semantic tagging standards such as Project Haystack, the Brick Schema, the Real Estate Core (REC), and the ASHRAE Standard 223P (a work in progress) are used to create a unified semantic model of the building. Ontologies can contribute to the interoperability of systems within a building by defining how two systems can communicate to accomplish a task as defined by the owners and operators. For example, ASHRAE 223P aims to normalize relationships between data, so that a sensor from one system and data from another system are both associated with a specific location in the building that is called the same thing. Connection Profiles (described in section 6, Orchestration) are another way to define the exact purpose of a connection between two systems. A Connection Profile enables systems to establish a 'contract/agreement' for the interactions, protocols, contexts, and data flows that are required for the systems to enact the purpose that's specifically defined by the profile.

### 50.1.5      APIs

An Application Programming Interface (API) is a software intermediary that enables two software applications to communicate with each other, so they can extract and share data within and across systems and organizations. The formal API consists of a set of definitions and protocols to build and integrate application software. Most companies that produce equipment or software say that they have an API and claim that they can 'integrate' with other systems. However, it's not unusual for two systems to be integrated, and yet unable to do useful work. This is the 'interoperability problem.' Verifying an API's documentation is critical to achieve reliable integrations. The API's documentation should include all necessary information to enable other software programmers to utilize data from the system. It should include a set of data points, a data architecture diagram, and library of programming commands to receive information from the system and write data points to the system. Not all APIs are created equal. Because exchanging data with other systems (from other manufacturers) is fairly new to building systems, there aren't many well-established smart building APIs. This is due, in part, to the fact that many building systems were developed for the vendor's proprietary platform, and the details of the API are not openly shared with outside vendors or customers. In addition, many APIs were created before mobile devices and applications were introduced, and they may not work effectively or efficiently with these technologies. The new standard for open data architectures where data is easily exchanged among all component systems is stretching older systems and applications in ways they were not designed to handle. A well-behaved API is easy to program (for software developers), exchanges (extracts and receives) the required data quickly and reliably for users, and is easy to maintain as the system's data architecture evolves over time. For a building this will span decades. APIs require systems at both ends of the API to exchange communication parameters to ensure secure and effective communication. For example, the URI is a parameter of the API service that the API client communicates with. If the URI of the service changes because of an upgrade or maintenance, all instances of the original URI on all of the client ends will no longer work.

Therefore, a critical part of a well-designed data and information exchange is a process to manage all of the APIs in the building's systems.

### 50.1.6      System Orchestration

Orchestration is the automated discovery, coordination, and management of the digital systems in buildings, including applications, data stores, and other services. A simple example of orchestration is the plug-and-play behavior of systems like USB that work with minimal if any, human intervention. An effective system orchestration automatically knows that a new system or device that's installed in a building should be securely connected to other compatible systems that are related to the new system/device and its location in the building, regardless of vendor, protocol, or any other variables. Orchestration is important in complex systems because it ensures that all of the necessary aspects of a system's interactions are properly configured, monitored, and adjusted, as the systems and their requirements change over the life of the building. Doing this with minimal human interaction significantly reduces errors and improves the overall efficiency of the building and its systems. Orchestration facilitates/enables connectivity (operation?) with growing number of domains that are outside of traditional building controls and automation, including: security, facility management (FM), ESG Reporting, ERP systems, CRM, grid interactivity, vertical transport, IAQ, office and access and visitor management systems. Orchestration can also facilitate the necessary protocol translations between systems that are typically incompatible and enable technicians to connect systems without knowing the details of domain-specific information. CNS/CP (Connectivity Naming System using Connection Profile) is an example of an open-source orchestration mechanism. CNS/CP enables a system to declare its ability to produce or consume standardized capabilities for a specific context. For example, a building system that needs to know the occupancy of room 123 in building X would declare such a need to the orchestrator. The orchestrator would, in turn, broker this need with the systems that can provide occupancy information for that room, and establish a match between the systems. Once matched, the CNS/CP orchestration securely provides both consuming and providing systems with all of the parameters necessary for the occupancy information to be conveyed with no additional human configuration.

### 50.1.7      Cloud-Native

The adoption of the cloud paradigm is an inescapable reality across all sectors in the 21st century. While most systems in buildings have been isolated in the past, as buildings rapidly adopt Industrial IoT and IT technologies and best practices, there is a solid argument that the future of buildings will include the widespread adoption of cloud-centric practices. Here, we are going beyond using the cloud simply as storage and beyond using the cloud as a way to consume SaaS offerings. The new reality is that the future of the cloud is a single, global computing environment with nodes (applications, devices, storage, and other systems) that communicate with each other using protocols and techniques that are native to the cloud. The term accepted in the IT world for this behavior is Cloud-Native. By around the 2030s, many buildings are anticipated to be Cloud-Native Buildings. This means that systems in such buildings would be able to call upon applications and consume or provide data from/to sources either in the building or in the cloud with the same ease. The value of the

ability for data and information to flow more easily is in stark contrast to the challenges practitioners have had in the past to access and use such data. This agility and flexibility are expected to provide building owners and operators with massive benefits from the adoption of innovation that can be easily deployed using Cloud-Native and tap into the vast amount of building-related data for the improvement in efficiency and performance of buildings. Cloud-Native approaches are beneficial for many building types in the following ways:
- For national or global portfolios of buildings that need to be operated and managed in a consistent manner.
- Smaller buildings that need to be managed remotely.
- Complex buildings with sophisticated IT departments wanting to monitor/manage BAS and related functions.
- Buildings needing to engage occupants with experiences such as Apps, kiosks, signage and social tools.

### 50.1.8      Cloud to On-prem

Buildings are complex physical entities, and operating a building begins and ends with the physical equipment. Most data and information that's exchanged between systems are local to the building, as described in Division 25.25.70 Control and Automation and pertaining to Division 25.25.80 Physical Elements. Most networking of the systems in 25.25.70 are locally connected with each other and to the physical elements for performance reasons. There is seldom a need for these systems to be located outside of the building premises for normal day-to-day operation of the building. Many of today's digital systems, as well as future systems, are being implemented on the Internet on what are commonly known as The Cloud. Cloud computing has tremendous advantages that are not available on-prem, such as shared and effectively unlimited computing and data storage capacities that are accessible globally. However, it's not always practical or necessary to use cloud computing for the building's local computing needs. That's because communication latency, security, and the quality/loss of the connection with the cloud may compromise the building's daily operations. It is important to consider how the building's on-prem digital systems will be connected to, and leverage, the capabilities of the Cloud in a secure and flexible manner that accommodates the changes that will occur over the long life of the building. The Interoperability Building Box (IBB) is a standardized way to gather and host systems that are located on-premises. The IBB can be a physical device, or run virtually in the building's datacenter, and address the owners' immediate requirements as well as future requirements that are unknown. The IBB is an 'open platform' for doing the following tasks:
- Hosting control "heads" for building systems
- Managing secure communications with on-prem systems
- Managing secure communication to the Internet cloud
- Enabling interoperation & message exchange between systems

- Providing local data storage to improve performance and efficiency. Building owners can specify the IBB as a component that's available from multiple vendors and in different configurations to suit the target building's requirements. The IBB enables system vendors to securely install and manage their software systems on the IBB, and securely & remotely manage their systems with accountability by a trusted service provider.

### 50.1.9      External Services

In addition to systems in the building that connect to Cloud services, buildings are increasingly benefiting from systems and services that are related to the purpose of the building. This includes enterprise systems for occupant experience, grid interactivity, regulatory compliance, emergency management, and many others.

## 50.2 Data and Information Portability

Data sources and destinations can exist on all tiers of the building control, management, and operations systems. Sensors create data, actuators consume data, controller manipulate data. Along the way, there is a requirement that the data have an established context so that it can be understood and used by "others". Others includes controllers, applications, interfaces, and services. More context is added such as location, frequency, range, duration, reliability, comparative parameters, historical analysis, and more. All of this requires a strong set of rules and objectives for how data is shared, how it is sourced, and what can the destination do with it.

## 50.3 What are well-behaved API's?

API stands for application programming interface - a set of definitions and protocols to build and integrate application software. An API is the software intermediary that allows two applications to talk to each other: the Interface. APIs are an accessible way (for programmers) to exchange data within and across systems. Most companies that produce equipment or software say that they can integrate with other systems, and that they have an API. A common statement is, "We can integrate with any system, as long as they use our platform". Proprietary platforms, databases, protocols, and data structures defeat the intention of smarter buildings. Defining requirements and verifying the API documentation is critical to achieve reliable project success. API documentation should include a set of data points or "points lists," a data architecture diagram, a well-defined owner-based nomenclature, detailed data semantics and metadata information, and a library of programming commands to receive information from the system and write data points to the system. Most critically, the API documentation should include all necessary information to enable other software programmers to utilize data from the system. Think of the API as a black box; inside the box is where the magic happens - that's the programming logic, the "secret sauce" that is the innovation of the supplier. How that black box communicates what it does, how to interact with it, what it can do, and how it can help other applications with their tasks is the role of the "interface". The data transferred via these interfaces may not be a single data point, it may be a collection of data such as a trend log, it may be an aggregated set of data such as the power requirements across multiple loads, or it may be even more complex data assemblies using constructs such as multi-state variables, variable arrays, time-based data, and compound data blocks using character string values, An example of a complex data set might be the time-based percentage of measured occupancy of a space versus the anticipated occupancy of that space with 15-minute intervals over an eight-hour period. Add in the historical information over a 90-day period to predict the cooling load of the HVAC system to optimize occupant comfort and reduce energy. Data sets can get arbitrarily complex as analytics tools and AI applications take raw and complex data into their applications and provide actionable results. Throw in "fuzzy logic", self-tuning, and predictive outcome-based routines and the level of complexity surpasses what most owners and engineers typically consider for their requirements. But advanced applications are now taking advantage of the available data and using it in these complex ways through modeling, simulations, and historical analysis to help predict future optimizations. Not all APIs are created equal. And because exchanging data with other systems is fairly new to building systems, smart building APIs are evolving and will become more well-established as their value increases. Many building systems were developed inside closed, proprietary platforms, the mechanics of which are not readily shared with outside vendors or customers. Many were created before we had mobile devices and apps and were not designed to work effectively or quickly there. The new standard for open data architectures where data is easily exchanged among all component systems is stretching older systems and applications in ways they were not designed to handle. Older systems and their associated applications may not be able to work within the new environment, however, there are vast number of "drivers" and interfaces openly available in an attempt to bring the old into the new. In many cases, these tools are simple converters from a proprietary format into one or more open formats. This can significantly benefit organizations with a multitude of older, incompatible, and non-interoperable systems.

A well-behaved API is easy to program (for software developers), exchanges (extracts and receives) the required data reliably and quickly for users, and is easy to maintain as things evolve in a multi-system data architecture.

## 50.4 General Data Exchange Requirements

- **A.** Use the same words for the same things, including the names associated with buildings, floors, rooms, zones, and spaces, across your whole smarter building portfolio. This includes acronyms, terms, definitions, naming standards, use of special characters, and more. Data standardization, naming conventions, and common ontologies (how things are assumed to be organized, which can be different between systems) need to be considered and agreed upon prior to implementation for any meaningful data and information exchange to occur. Please refer to section 25.25.60.
- **B.** All data will be normalized, as per 25.25.60. This is often a task of the BMS front end software applications which contains the database, user interface, and translation and normalization tools. Simple normalization might be converting units. Another might be changing a name.
- **C.** Applications utilize the API tools as determined by the owner/tenant.
- **D.** Applications will utilize the owner and/or tenant provided common naming conventions for assets, spaces, and zones (preferably with universal unique identification UUIDs tags) to ensure interoperability and ease of configuration.
- **E.** Applications will have the capability to send and receive commands and data from other systems and interact via openly published API commands or similar IP-based open data exchange methods.
- **F.** Applications follow the appropriate exchange open-standards and protocols based upon the provided owner and tenant requirements. (This information has to be defined in a specification language prepared by qualified design professionals.)
- **G.** The exchange of data uses open and currently accepted and published mechanisms. Examples of current open data exchange mechanisms include BACnet IP, LON IP, MODBUS IP, RESTful, MQTT, OBIX, and OPC. While some of those listed here are considered "protocols" for data communications, they do, as part of their standards, define many of the details necessary for improved interoperability. For ontologies, tools such as Haystack, Brick, ASHRAE's S223P Semantic Interoperability are useful starting points for developing owner focused standards. It is also important to understand the mechanisms may differ with device-to-device, device-to-system, and system-to-system data exchanges. Choosing the right set of tools will be dictated by the data source and destination requirements.
- **H.** Data exchanges shall be based on established information models.
- **I.** All data exchange mechanisms will be resilient by established government standards.
- **J.** All data exchanges shall follow recommended cybersecurity requirements outlined in section 25.25.95. An example for a highly secure environment is the requirement that every data exchange must provide end-to-end encryption of data.

- **K.** Data that contains PII (Personally Identifiable Information) shall be separated and identified as such. Building automation data that may contain personal information might include the name associated with an office, the temperature setpoint default of a space associated with an individual's profile, user access logs, all access credential information, all security/access credentials, and usage logs, etc. While these are uncommon in typical BAS designs, the installer and integrator must be aware of any data that may be considered PII or owner confidential.

## 50.5 Example Requirements for Project Purposes/Goals

Below are some examples outlining what would need to be defined for data and information exchange specific to certain project goals. Your Owner's Project Requirements doc should include similar details specific to your project goals.

### 50.5.1      Enabling Remote and Efficient Building Operations

If a goal is to empower building operations, management, automation, and reporting by asset (such as elevator, air handling unit, or lighting ballast), require data about the following to be exchanged and available across systems:
- **A.** Schedule requirements - normal hours of operation, shoulder hours, off hours, etc.
- **B.** Utility utilization / metering data (instantaneous power usage and storage capacity when possible)
- **C.** Automation interoperability, triggering or receiving commands as appropriate.
- **D.** System alarm, alert, and event notification
- **E.** Ticket tracking in conjunction with service, scheduled maintenance, and failure repair
- **F.** Remote application interface to view, configure, and manage the above information.

### 50.5.2      Contact-less Tenant Experience

If a goal for a multi-tenant space such as an office building is to deliver a contact-less tenant experience and if you require data from the systems to be exchanged and available across systems, then an approved access control credential (key card, fob, phone app, etc.) can be utilized to trigger any of the following, :
- **A.** Parking (gate opening, charging, tracking, etc.)
- **B.** Elevator control (taking tenant to pre-programmed floor)
- **C.** Door control and access control (opening and closing)
- **D.** Room scheduling and booking
- **E.** Unified communications call launch in collaboration spaces
- **F.** Access to room control systems (for lighting, shades, temperature, and audiovisual devices) and associated extra services such as food ordering / in-room dining, etc. based upon the building type.

- **G.** Point of sale (POS) integration for cafeterias and vending
- **H.** Fitness center access and machine control

### 50.5.3      Grid-Interactive Efficient Building

Based upon grid signals for price or carbon offsets, automating and optimizing building performance, building systems should have the following:
- **A.** States of operation:
  - **A.1.** Running or Idle Normal, Running or Idle Curtailed, Running or Idle Heightened, Override On/Off, Cycling
- **B.** Electrical Usage:
  - **B.1.** Instantaneous power usage and/or storage capacity (when appropriate)
- **C.** Grid Interactivity Response:
  - **C.1.** 1-3 levels of Shed (use less energy or release stored energy) and 1-2 levels of Load Up (use or store more energy)

### 50.5.4      Return-to-Work Efficiencies Based on Occupancy

Many commercial buildings are challenged to run efficiently as people return to work after the COVID pandemic, and want to use space occupancy to automate and optimize building performance. To facilitate that, all building systems should have the following:
- **A.** Data on states of operation:
  - **A.1.** Active daytime state
  - **A.2.** Standby daytime state (with appropriate recovery based upon system)
  - **A.3.** Active off-hours state
  - **A.4.** Quiescent / overnight state (off or lowest consumption mode)
- **B.** Based upon the states above, be able to operate the following energy-consuming or energy-conserving systems:
  - **B.1.** Lighting control (recalling appropriate scene)
  - **B.2.** Shade control
  - **B.3.** Temperature control
  - **B.4.** AV and multimedia systems
  - **B.5.** Elevators, escalators, and conveyance systems
  - **B.6.** On site energy storage

### 50.5.5      Modeling and Simulation of Building Operations

Modeling and simulation of building operations is an important consideration for data and information exchange. Modeling can be utilized to estimate the energy use impact of major, capital-intensive changes such as reglazing or switching to an all-electric approach for heating and hot water. Modeling can also be used to test out

different space utilization plans to optimize the use of both space and utilities. All the data sets described in the use cases above contribute to more accurate granular modeling. These "digital twin" uses of data will become increasingly important as tools and applications are developed that will require data on broader and deeper level. The use of cloud computing resources for modeling will make this type of real estate asset management possible. If your design team plans to model or simulate building operations, you should define the outcomes they expect, and the data they will need in the design and specification and list modeling as an important Application in section 25.25.40 above.
